Plano de infra cloud

Três planos Terraform para tirar o DEF do túnel Cloudflare e colocá-lo em nuvem: Google Cloud, AWS e Azure. Mesmo desenho nos três: site serverless que escala a zero, a esteira de produtos rodando como jobs de container disparados por cron e por evento, banco gerenciado, object storage no lugar do MinIO, segredos no cofre e deploy por GitHub Actions sem chave estática.

Resumo executivo

O stack já é todo container (Flask + Playwright, Nginx + React, OCR em imagem pronta), então a mudança não é reescrever: é trocar o docker compose por serviços gerenciados e trocar o make manual por gatilhos. A recomendação é começar pelo GCP: Cloud Run Jobs aceita a imagem atual sem adaptação, monta buckets como pasta (o staging/ continua sendo uma pasta) e tem a menor lista de mudanças de código. A AWS tem o menor custo no cenário recomendado, mas pede o adaptador Lambda, um NAT e cuidado com o webhook atrás do CloudFront. A Azure tem a melhor paridade de jobs (cron e evento nativos), mas o Blob não fala S3 e isso obriga um adaptador de storage.

Decisões que valem para os três

  • Uma imagem, vários papéis. infra/docker/Dockerfile.site é uma camada fina sobre a imagem atual que troca python main.py por gunicorn. O serviço web e todos os jobs usam a mesma imagem; só o comando muda.
  • Nginx + Flask no mesmo pod. Dockerfile.web builda o React e sobe o Nginx em :8080 fazendo proxy para 127.0.0.1:5000. É o mesmo roteamento de nginx/nginx-react.conf (+ secao5), sem TLS, que passa a terminar no balanceador. Na AWS o React vai para S3/CloudFront e o Flask fica sozinho no Lambda.
  • OCR só quando precisa. O info-scrap roda como sidecar dentro do job (GCP, AWS) ou como app interno que escala a zero (Azure). Custo ocioso zero.
  • Pastas viram volumes. staging/, uploads/ e config/ml_tokens.json são montados em /app/... a partir de GCS FUSE, EFS ou Azure Files. Os scripts continuam lendo e gravando pasta.
  • Gatilhos, não cron no host. Cron gerenciado (fuso America/Sao_Paulo) e fila de eventos para o webhook do ML. Jobs destrutivos (reprice-all) existem, mas nunca entram no cron por padrão.
  • Sem segredo no git. Secret Manager, SSM Parameter Store ou Key Vault; o Terraform cria o cofre e ignora rotação feita por fora. CI autentica por OIDC (Workload Identity, IAM role ou credencial federada), sem chave JSON.
  • Orçamento com alarme (50/90/100 % de US$ 60) e alerta de erro 5xx/job falho em cada nuvem.
  • LLM e vetores sem Ollama. Qdrant, Ollama e hsmart não sobem na nuvem: pgvector no Postgres gerenciado e, se enable_llm=true, Vertex AI, Bedrock ou Azure OpenAI. O OpenAI gpt-4o-mini já em uso continua funcionando como está.

Princípios de desenho

Serverless onde cabe

  • Web escala a zero (Cloud Run, Lambda, Container Apps). Tráfego de catálogo de afiliados é baixo e cacheável; CDN na frente.
  • Jobs pagam por minuto de execução. A esteira roda ~1 h/dia: custa centavos.
  • Banco é o único componente sempre ligado. Menor instância que aguenta Postgres 16 com pgvector.
  • Redis vira opcional: o site não depende dele, só os agentes e o oracle.

Estado da arte de gatilhos

  • Cron gerenciado chama a API de execução do job passando overrides de argumentos: um job prepare-ml, N URLs.
  • Evento = mensagem JSON {"job":"api-update-ml","args":[...]}. O orquestrador (Workflows / Step Functions / KEDA) resolve o job e espera terminar.
  • Encadeamento noturno (preços → verificação → tags) como fluxo declarativo, com retry e log por etapa.
  • Tudo em Terraform: adicionar um job é adicionar uma entrada no mapa local.jobs.

O LB global é o único item "fixo" caro. Alternativa a custo zero: enable_lb=false e Firebase Hosting com rewrite para o Cloud Run (domínio + TLS + CDN grátis); o README do módulo descreve. Domain mapping direto do Cloud Run não cobre southamerica-east1.

Pontos de atenção

  • Sidecar OCR em job: o container site declara depends_on = ["ocr"] e o sidecar tem startup probe TCP (obrigatório). A documentação do Google não afirma explicitamente que o sidecar é encerrado quando o principal termina; por isso existe ocr_mode = "service", que sobe um Cloud Run interno def-prd-ocr (min 0) com Direct VPC egress.
  • Há um problema conhecido do Cloud Run com multi-container + conexão Cloud SQL embutida (volume /cloudsql); o README descreve o caminho alternativo por IP privado se aparecer.
  • O primeiro apply falha no Cloud Run se as imagens ainda não existem: aplicar com -target APIs e registry, fazer push, depois o apply completo.
  • GCS FUSE grava o arquivo inteiro a cada write: ótimo para JSONs de staging e tokens, ruim para milhares de arquivos pequenos. Para uploads/ grandes, prefira enviar direto ao bucket de mídia.
  • Nomes de bucket são globais: o código precisa parar de criar um bucket por plataforma (mercadolivre, shopee…) e usar MINIO_BUCKET com prefixo (ver Δ código).

Plano 2 AWS — Lambda + CloudFront + ECS Fargate Spot

O plano mais barato no mínimo e o mais "serverless puro": o Flask roda em Lambda a partir da imagem atual com o Lambda Web Adapter (sem reescrever rotas), o React vai para S3 com CloudFront na frente e os jobs rodam em Fargate Spot (até 70 % mais barato) sem nenhum cluster ligado. Região padrão us-east-1; sa-east-1 tem tudo, mas custa ~30–40 % mais.

Pontos de atenção

  • NAT é obrigatório para o Lambda (chamadas ao ML e à OpenAI saem da VPC). O fck-nat resolve por ~US$ 7; o NAT Gateway gerenciado custaria ~US$ 33 + US$ 0,045/GB. Os jobs fogem disso rodando em sub-rede pública com IP público.
  • Cold start do Flask em container ~3–5 s na primeira requisição depois de ociosidade. O cache de 60 s do CloudFront em /api/* e o /health da CDN amortecem; provisioned concurrency resolveria por ~US$ 12/mês.
  • No Lambda o sistema de arquivos é somente leitura (exceto /tmp); o /app/config vira link para o EFS. Só os jobs escrevem em staging/.
  • REDIS_URL no ElastiCache Serverless é TLS (rediss://); o cliente Python já suporta.
  • Function URL atrás do CloudFront: com OAC (AWS_IAM) todo POST/PUT precisa do header x-amz-content-sha256, que o webhook do ML não manda. Para a F2, usar lambda_url_auth_type = "NONE" e conferir no Flask o header secreto x-origin-verify que o CloudFront injeta (Δ código pequeno).

Plano 3 Azure — Container Apps + Container Apps Jobs

Azure Container Apps é, dos três, o que mais parece o docker compose: app com dois containers, jobs com cron e gatilho por fila (KEDA) nativos, volume Azure Files por mount e domínio com certificado gerenciado grátis. O preço disso é o storage: o Blob não tem API S3, então o cliente MinIO precisa de um adaptador. Região padrão eastus; brazilsouth tem tudo e custa ~40 % mais.

Pontos de atenção

  • Adaptador de storage é obrigatório: services/minio_client.py, routes/media_routes.py e scripts/stage_products.py falam S3. Com azure-storage-blob o Δ é pequeno (upload + URL pública), mas existe.
  • Azure Files é SMB: ótimo para dezenas de JSONs, lento para milhares de arquivos pequenos.
  • Com min_replicas=0 a primeira requisição espera ~5–10 s; o OCR interno também parte de zero (~10–20 s na primeira chamada do job).
  • Domínio em dois passos: apply com enable_custom_domain=false, criar o TXT asuid e o CNAME com os valores das saídas, depois apply de novo. Domínio apex (sem www) exige az containerapp hostname bind --validation-method TXT à mão.

Roteiro de implantação

  1. F0 primeiro. Tirar segredos do git, rotacionar ML_CLIENT_SECRET, consertar o db do webhook. Nada disso depende de nuvem.
  2. Aplicar os Δ 2, 3, 5, 6, 7 e rodar make test-unit. Testar local com docker compose apontando MINIO_SECURE=false.
  3. Escolher a nuvem (padrão: GCP) e preencher terraform.tfvars: domínio, e-mail de alerta, conta de billing, segredos. Nada de valor sensível commitado.
  4. Bootstrap do state e terraform apply. Primeira aplicação cria banco, buckets, cofre, jobs, cron (desligados), CDN/LB. ~15 min.
  5. Build e push das imagens (def-site, def-web) pelo workflow de exemplo ou à mão; terraform apply -var image_tag=….
  6. Migrar dados. pg_dump → import; mc mirror → gcloud storage rsync / aws s3 sync / azcopy; copiar staging/, uploads/, ml_tokens.json para o volume. Reescrever as URLs de imagem no banco para o novo bucket (script de uma linha SQL).
  7. DNS no Cloudflare (só DNS, sem proxy laranja) e ML_REDIRECT_URI novo no DevCenter. Refazer o login OAuth do ML uma vez.
  8. Fumaça: /health, /api/products?limit=3, uma imagem em /media/…, prepare-ml manual com uma URL, stage, conferir no site.
  9. Ligar o cron (schedules.nightly.enabled=true) e observar 2–3 noites nos logs. publish e populate-mf continuam desligados até a F2 (preço numérico, soft delete).
  10. Desligar o túnel e o PC: serve-cloudflare vira comando de desenvolvimento. Atualizar CLAUDE.md §2.2 e §3.
